A Bit of History

  • Founded in 2007 by Willow Garage at the Stanford Artificial Intelligence Lab.
  • Since 2013 managed by OSRF (Open Source Robotics Foundation).
  • ROS 2 started in 2014 to address limitations of ROS 1.
  • Current ROS 2 release: Jazzy Jalisco (May 2024), supported until May 2029.
  • We will use: Humble Hawksbill (May 2022), supported until May 2027.
  • ROS 2 built on DDS (Data Distribution Service) for real-time, reliable communication.
  • Find out more in the Red Hat - How to Start a Robot Revolution series.

What is ROS / ROS 2?

  • ROS stands for Robot Operating System.
  • It is not a computer operating system, but a middleware or a Meta Operating System that increases the system’s capabilities for robotic applications.
  • ROS 2 is the second generation of this middleware.
  • ROS is fundamentally an open-source software released under licenses like Apache 2 and BSD.
  • ROS provides standardized communication protocols, libraries, and tools to facilitate robot software development.
  • The fundamental difference distinguishing ROS from other middlewares is its vast developers community around the world.

Why ROS?

  • Open Source: Active community, still evolving and improving.
  • Development Tools: Debugging tools, 2D & 3D visualization tools, logging tools, simulation tools.
  • Modularity: Build complex systems from smaller, reusable components.
  • Hardware Abstraction: Works with various hardware platforms and sensors.
  • Scalability: From small robots to large multi-robot systems.
  • Open Source
    • Free to use and modify
    • Large community contributing code and support
  • Development Tools
    • Tools for debugging, visualization, and simulation
    • Makes development faster and easier
    • Try ideas safely and quickly before using real robots
    • Repeat scenarios to learn and improve
  • Modularity
    • Build with small, focused parts that fit together
    • Easier to change one part without breaking the rest
  • Hardware Abstraction
    • Works with many different robots and sensors
    • Easier to switch hardware without changing software
  • Scalability
    • From small robots to big multi-robot systems
    • Grows with your project needs

Also discuss:

  • CI/CD (Continuous Integration/Delivery)
    • Regular, small updates with automatic checks
    • Catch issues early and keep quality high
  • Containerization
    • Package everything so it runs the same everywhere
    • Fewer “works on my machine” problems

Three Dimensions of ROS 2

ROS 2 is approached from three different but complementary dimensions:

  1. The Community: A fundamental element where developers contribute applications and utilities through public repositories.
  2. The Computation Graph: A representation of the running ROS 2 application, composed of nodes and arcs.
  3. The Workspace: The static set of software installed on the computer/robot, including development tools and the build system (Colcon).

Nodes and Execution

  • Let’s see the nodes in action using the turtlesim example again.

Nodes communicate using different paradigms:

  • Publication/Subscription (Topics): Asynchronous communication where N nodes publish messages to a topic that reaches M subscribers. This is the most common type.
  • Services: Asynchronous 1:1 communication where a node requests another and expects an immediate response. In ROS 1, this was synchronous, but this is not recommended in ROS 2.
  • Actions: Asynchronous 1:1 communication for requests that take time to complete, allowing the calling node to receive periodic feedback.

Publication/Subscription (Topics)

  • Publisher: The node that sends messages to a topic.
  • Subscriber: The node that receives messages from a topic.
  • Topics: The name of a data stream (e.g., /camera_image).
  • Messages: The actual data. A specific, defined format (e.g., String, Image).

In rqt, topic Monitor from the menu bar at the top. Run ros2 topic list -t to see all topics with their types. Run the teleop node: ros2 run turtlesim turtle_teleop_key Try publishing with the teleop node, to the /turtle1/cmd_vel topic to move the turtle using rqt, or with the terminal: ros2 topic pub /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}" Run ros2 topic info /turtle1/cmd_vel --verbose to see publishers and subscribers. Run ros2 interface show geometry_msgs/msg/Twist to see the message structure.

Services (Request/Response)

  • Service Server: The node that offers a service.
  • Service Client: The node that calls the service.
  • Service: A named request/reply interaction (e.g., /spawn_turtle).
  • Request/Response: The data sent to and received from the service.

In rqt, service Caller from the menu bar at the top. Run ros2 service list to see all available services. Run ros2 service info /turtle1/set_pen --verbose to see the service type and nodes. Run ros2 interface show turtlesim/srv/SetPen to see the service structure. Try the set_pen service to change the turtle’s pen color using the service caller in rqt or with the terminal: ros2 service call /turtle1/set_pen turtlesim/srv/SetPen "{r: 255, g: 0, b: 0, width: 5, off: 0}" Spawn a new turtle: ros2 service call /spawn turtlesim/srv/Spawn "{x: 2.0, y: 2.0, theta: 0.0, name: 'turtle2'}"

Actions (Long-running)

What if completion takes time?

  • Action Server: The node that performs the action.
  • Action Client: The node that requests the action.
  • Action: A named long-running request/feedback/reply interaction (e.g., /turtle1/rotate_absolute).
  • Goal/Feedback/Result: The data sent to, received during, and returned from the action.

In rqt, action Client from the menu bar at the top. Run ros2 action list to see all available actions. Run ros2 action info /turtle1/rotate_absolute --verbose to see the action type and nodes. Run ros2 interface show turtlesim/action/RotateAbsolute to see the action structure. Use the action client in rqt or with the terminal: ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.57, angular_speed: 1.0}"

— PUBLISHER CODE —

import rclpy
from rclpy.node import Node

from std_msgs.msg import String


class MinimalPublisher(Node):

    def __init__(self):
        super().__init__('minimal_publisher')
        self.publisher_ = self.create_publisher(String, 'topic', 10)
        timer_period = 0.5  # seconds
        self.timer = self.create_timer(timer_period, self.timer_callback)
        self.i = 0

    def timer_callback(self):
        msg = String()
        msg.data = 'Hello World: %d' % self.i
        self.publisher_.publish(msg)
        self.get_logger().info('Publishing: "%s"' % msg.data)
        self.i += 1


def main(args=None):
    rclpy.init(args=args)

    minimal_publisher = MinimalPublisher()

    rclpy.spin(minimal_publisher)

    # Destroy the node explicitly
    # (optional - otherwise it will be done automatically
    # when the garbage collector destroys the node object)
    minimal_publisher.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

import rclpy

from std_msgs.msg import String


class MinimalSubscriber(Node):

    def __init__(self):
        super().__init__('minimal_subscriber')
        self.subscription = self.create_subscription(
            String,
            'topic',

— SERVICE SERVER CODE —

from example_interfaces.srv import AddTwoInts

import rclpy
from rclpy.node import Node


class MinimalService(Node):

    def __init__(self):
        super().__init__('minimal_service')
        self.srv = self.create_service(AddTwoInts, 'add_two_ints', self.add_two_ints_callback)

    def add_two_ints_callback(self, request, response):
        response.sum = request.a + request.b
        self.get_logger().info('Incoming request\na: %d b: %d' % (request.a, request.b))

        return response


def main():
    rclpy.init()

    minimal_service = MinimalService()

    rclpy.spin(minimal_service)

    rclpy.shutdown()


if __name__ == '__main__':
    main()

— SERVICE CLIENT CODE —

import sys

from example_interfaces.srv import AddTwoInts
import rclpy
from rclpy.node import Node


class MinimalClientAsync(Node):

    def __init__(self):
        super().__init__('minimal_client_async')
        self.cli = self.create_client(AddTwoInts, 'add_two_ints')
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('service not available, waiting again...')
        self.req = AddTwoInts.Request()

    def send_request(self, a, b):
        self.req.a = a
        self.req.b = b
        return self.cli.call_async(self.req)


def main():
    rclpy.init()

    minimal_client = MinimalClientAsync()
    future = minimal_client.send_request(int(sys.argv[1]), int(sys.argv[2]))
    rclpy.spin_until_future_complete(minimal_client, future)
    response = future.result()
    minimal_client.get_logger().info(
        'Result of add_two_ints: for %d + %d = %d' %
        (int(sys.argv[1]), int(sys.argv[2]), response.sum))

    minimal_client.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

Action Anatomy

Why an Action?

  • Long‑running (timed) pump operations
  • Feedback for UI / CLI progress
  • Cancel for emergency stop

Ask them why an Action is used here instead of a Service or Topic. Actions are suitable for operations that take time to complete and require feedback or the ability to cancel. In this case, pumping operations can take several seconds, and we want to provide feedback on progress and allow for cancellation in case of emergencies.

PumpStep.action (conceptual):

# Goal
bool state      # enable (true) or disable (false)
int32 speed     # firmware speed value
bool dir        # true forward / false reverse
int32 duration_ms
---
# Result
bool success
string message
---
# Feedback
float32 progress_pct    # 0.0 -> 100.0
int32 elapsed_ms

Topic State

State message (simplified):

bool running
int32 speed
bool dir
int32 remaining_ms

Publishing rate parameter: state_publish_rate_hz (default 2.0).

Use it for dashboards & health monitoring (low frequency).

Simulation vs Hardware

Parameter controls:

  • simulated: mock driver when true
  • device_id: serial identifier or auto-detect
  • feedback_rate_hz: action feedback granularity

Design implication: Keep abstraction boundary so REST layer does not depend on simulated/hardware choice.
